# 설계 — AI 개발 능력을 기르는 피드백 도구

2026-10-02. 근거는 `evidence.md`, 보이는 모습은 `images/report-ko.png`·`report-en.png`(지어낸 데이터로 그린 예시, `scripts/demo.mjs`). 리포트·질문은 한국어와 영어(`--lang`).

## 무엇을 하는 도구인가

AI 코딩 에이전트와 일하는 개발자가 **자기 기록을 보고 스스로 깨닫게** 하는 도구다. 읽고 나면 네 가지에 답할 수 있어야 한다.

1. 나는 지금 어떻게 개발하고 있나
2. 무엇을 바꾸면 좋을까
3. 왜 그런가 (근거)
4. 앞으로 어떻게 할까

하지 않는 것: 점수·등급·순위·연속 기록, 속도·사용량 지표, 성향 라벨, 팀·관리자 화면, 도구마다 갈리는 조언, 출처를 댈 수 없는 조언. 훈련 계획이나 면접 준비 같은 코칭도 하지 않는다.

code-dependent(재미로 보는 거울)와는 따로 둔다. 로그 읽기·캐시·비밀값 가리기·「안 돼」 반복 찾기 코드는 그쪽에서 가져다 쓴다.

## 원칙 (evidence.md 1절의 요약)

- 사람이 아니라 **그때의 행동**을, 실제 메시지·시각·커밋으로 보여 준다.
- 피드백 하나는 **무슨 일이 있었나 → 왜 문제인가 → 이렇게 해 보세요 → 스스로 확인해 보기**로 끝까지 간다. 경고만 하지 않는다.
- 한 번에 **많아야 둘**. 다음 달 목표는 **하나**.
- 잘하는 것도 「칭찬」이 아니라 **왜 계속 지키면 좋은지**로 쓴다.
- **남이 아니라 지난 나**와 비교한다.
- 막지 않는다. 비밀값 전송과 되돌릴 수 없는 명령만 예외.
- 기록만으로 가를 수 없는 것은 그렇다고 쓴다(예: 해결이 메시지 덕인지 모델이 바뀐 덕인지).

## 읽는 데이터

| 데이터 | 꺼내는 것 |
|---|---|
| 에이전트 대화 기록 (Claude Code `~/.claude/projects`, Codex `~/.codex/sessions`) | 내 메시지, 에이전트 답의 끝부분, 도구 실행과 성공·실패, 모델·버전·effort·권한 모드, 시각 |
| git (각 프로젝트 폴더) | 커밋, diff, 어떤 줄이 언제 다시 바뀌었나 |
| 테스트·빌드 결과 | 대화 속 실행 기록의 성공·실패 |
| 지침 파일 (CLAUDE.md, AGENTS.md, 메모리) | 규칙 문장 — 위반을 그 문장으로 짚을 때 |

**모두 내 기기 안에서 처리한다.** 밖으로 나가는 것은 짧은 문장 분류(의도·정정 여부)뿐이고, 보내기 전에 비밀값·개인정보를 가린다. 끌 수 있고, 끄면 규칙으로 잡는 피드백만 나온다. 결과와 개인 기록은 `~/.ai-dev-feedback/` 에 둔다.

## 처리 흐름

```
읽기 → 사건 만들기 → 피드백 찾기 → 고르기 → 문장 만들기 → 리포트
```

1. **사건 만들기**: 요청·답·도구 실행·테스트 결과·편집·커밋을 프로젝트별 시간순 한 줄로. 같은 대화가 이어진 기록은 한 번만 센다.
2. **피드백 찾기**: `evidence.md` 2절의 C1~C14 를 아래 방법으로 찾는다.
3. **고르기**: 아래 「고르는 법」.
4. **문장 만들기**: 아래 「문장 규칙」. 근거 문장은 미리 확인해 둔 카탈로그에서만 가져온다.
5. **리포트**: HTML 한 장. 로컬에서 연다.

## 피드백 찾는 법

**규칙** = 코드로 셈, 비용 없음. **분류** = 짧은 문장을 작은 모델로 분류, 결과 캐시.

| # | 피드백 | 찾는 법 | 방식 | 필요한 것 |
|---|---|---|---|---|
| C1 | 낯선 기술을 설명 없이 받기만 함 | 그 프로젝트에 처음 들어온 의존성·import 를 다룬 대화에서 「왜·어떻게」 의도가 있었나 | 규칙 + 분류 | git |
| C2 | 같은 증상에 「고쳐 줘」만 반복 | 원인 짐작 없는 수정 요청 3번 이상 연속(30분 넘게 끊기면 따로) | 분류 + 규칙 | code-dependent 구현 있음 |
| C3 | 「완료」 뒤 실패 보고 | 에이전트의 완료 주장 → 이어진 3턴 안에 사용자의 실패 보고 | 분류 + 규칙 | |
| C4 | 완료 전 테스트 안 돌림 | 완료 주장 직전 턴에 테스트·빌드·린트 실행이 있었나 | 규칙 | 명령 분류는 code-dependent 에 있음 |
| C5 | 기대값 확인 없는 테스트 | 새 테스트 함수에 assert·expect 가 없거나 「예외 안 남」만 확인 | 규칙(언어별) | git |
| C6 | 테스트 기대값을 고쳐 통과시킴 | 같은 커밋에서 구현과 기존 테스트 기대값이 함께 바뀜, skip·only 추가 | 규칙 | git |
| C7 | 보안 경로를 검사 없이 바꿈 | 인증·권한·결제·입력 경로 변경에 관련 테스트·정적 분석 실행 없음 | 규칙(경로 목록은 사용자가 고침) | git |
| C8 | 첫 지시에 완료 기준 없음 | 새 작업 첫 요청의 네 요소 | 분류 | **정확도 측정 필수** |
| C9 | 정정 턴이 많음 | 정정·실패 보고·중단 비율 | 분류 | |
| C10 | 에이전트 코드가 버려지거나 곧 다시 고쳐짐 | 대화 속 편집과 git 대조: 커밋까지 남았나, 사흘 안에 다시 바뀌었나 | 규칙 | git |
| C11 | 한 번에 너무 많이 맡김 · 커밋이 큼 | 한 요청의 요구 수, 커밋당 크기·섞인 주제 | 분류 + 규칙 | git |
| C12 | 같은 교정을 여러 대화에서 반복 | 뜻이 같은 교정을 묶어 서로 다른 대화 수를 셈 | 분류(묶기) | |
| C13 | 규칙으로 적었는데도 또 어겨짐 | C12 의 교정이 지침·메모리의 어느 규칙과 같은 뜻인지 대조 | 분류(대조) | 지침 파일 |
| C14 | 비밀값 · 되돌릴 수 없는 명령 | 패턴 | 규칙 | code-dependent 구현 있음 |

### 정확도 검증

- 피드백마다 내 기록에서 50건 안팎을 뽑아 사람이 「맞다/아니다」를 붙인다(정답 표본).
- **맞는 비율이 80% 를 넘는 피드백만 리포트에 나온다.** 못 넘으면 「아직 재는 중」으로 숨긴다.
- 결과는 `docs/accuracy.md` 에 남긴다. 규칙을 바꾸면 다시 잰다.

## 고르는 법 (사람에 맞추기)

맞춤은 **무엇을·언제·어떻게** 보여 줄지만 바꾼다. 무엇이 맞는지는 바꾸지 않는다 — 내용은 C1~C14 안에서만 나온다.

| 개인 기록 | 쓰는 곳 |
|---|---|
| 피드백별 기준선(요청 100개당, 작업 하나당) | 「지난달보다」. 첫 2~4주는 기준선을 쌓느라 비교하지 않는다 |
| 익숙한 기술 목록(프로젝트·라이브러리별 경험) | C1 을 낯선 곳에서만 짚음 |
| 잘하는 것(기준선이 이미 좋은 피드백) | 「잘하고 있는 것」 절로 가고, 바꿀 것 후보에서 빠짐 |
| 잘했던 순간(같은 종류의 문제를 빨리 푼 메시지) | 「이렇게 해 보세요」의 내 예시 |
| 내 규칙(지침·메모리 문장) | C13 을 그 문장으로 짚음 |
| 다음 달 약속과 그 결과 | 다음 리포트 첫머리 |

**바꿀 것 고르기**: 후보마다 `샌 크기(시간 또는 횟수) × 기준선보다 나빠진 정도 × 정확도` 로 줄 세워 **위에서 둘**. 첫 달은 기준선이 없으니 샌 크기만 본다.

**잘하는 것 고르기**: 기준선이 좋고 근거가 ✔ 인 것 중 **셋**.

## 문장 규칙

- 쉬운 말. 「신호·기준선·단언·오라클」 같은 말을 쓰지 않는다(「결과가 맞는지 확인」).
- 숫자는 실제로 센 것만. 아직 못 재는 것은 맨 끝 「다음 달부터 함께 볼 것」에 한 줄로.
- 내 메시지는 원문 그대로 인용하고 날짜·프로젝트·맥락을 붙인다(예: 「배포 설정을 바꾸며」).
- 근거 문장은 `evidence.md` 에서 **✔ 인 출처만**, 원문 뜻을 넘지 않게. 숫자에는 표본 크기를 붙인다(「52명, 채팅형 AI」).
- 기록만으로 가를 수 없는 것은 「공정하게 말하면」 상자로 밝힌다.
- 「이렇게 해 보세요」에는 **그대로 보낼 수 있는 문장**을 준다.
- 도구·모델마다 갈리는 조언은 쓰지 않는다. 「다음에는」은 사용자의 행동으로.

## 리포트 모양 (images/report-ko.png)

### 월간 돌아보기 — 한 달에 한 번

1. **한 줄로 보면** — 잘하는 것 한 마디, 시간이 가장 많이 샌 곳, 반복된 문제. 그 아래 이 문서에 무엇이 있는지 세 줄과 프로젝트·대화·메시지 수.
2. **잘하고 있는 것** (셋) — 제목, 실제 근거(숫자나 내 메시지), 왜 계속 지키면 좋은지와 출처.
3. **바꾸면 좋을 습관** (많아야 둘) — 각각
   - 무슨 일이 있었나: 이번 달 전체 숫자 → 가장 큰 사례 하나를 시간순으로 → 그날 가장 잘한 순간
   - 왜 문제인가: 쉬운 설명 한 단락 + 출처가 붙은 근거 목록 + 내 규칙과 겹치면 그 문장
   - 이렇게 해 보세요: 그대로 보낼 문장
   - 스스로 확인해 보기: 질문 한두 개
4. **다음 달에 해 볼 한 가지** — 「[상황]이면 [행동]」 한 문장. 다음 달 리포트가 이 상황이 몇 번 있었고 몇 번 지켰는지 보여 준다고 알린다.
5. **다음 달부터 함께 볼 것** — 아직 못 재는 것.
6. **출처** — 번호 목록, 원문 대조 날짜.
7. **맺음말** — 무엇을 읽었고, 비교하지 않으며, 기록에 안 남는 일(직접 읽기·고치기)은 반영되지 않는다는 것.

두 번째 달부터는 1번 앞에 **지난달 약속 돌아보기**가 붙는다(상황 몇 번, 지킨 것 몇 번, 그때와 아닐 때의 차이).

### 작업 회고 — 작업 하나가 끝났을 때 (2단계)

같은 모양을 작업 하나에 적용한다. 맨 앞에 「이 작업에서 가장 오래 걸린 곳은 어디였다고 생각하세요?」를 먼저 묻고, 답과 기록이 다르면 그 차이를 먼저 보여 준다(확신했는데 틀린 순간이 가장 잘 배우는 순간).

### 작업 중 알림 — Claude Code 훅 (3단계)

- 비밀값이 든 메시지: 보내기 전에 막는다.
- 같은 증상으로 세 번째 수정 요청: 보내기 직전에 한 줄 제안(막지 않음). 지난 약속과 내가 잘했던 메시지를 인용.
- 테스트 실행 없이 끝난 「완료」: 턴이 끝난 뒤 한 줄.
- 같은 원인은 대화당 한 번, 하루 상한. 약속을 세 번 연속 지키면 그 알림을 끈다. 무시율을 잰다.

### 시작할 때 고르는 것

code-dependent 와 같은 흐름이다: 기록을 먼저 훑고 → 선택지마다 메시지 수·예상 비용과 「고르면 무엇이 나오고 무엇이 빠지는지」를 붙여 보여 주고 → 고른 뒤 실행. 고른 것은 기억해 두고, 다음엔 「지난번과 같이」 한 번으로 시작한다.

```
[무엇을 돌아볼까요?]
  1) 지난 30일 — 메시지 1,200개 (추천)
  2) 지난 7일 — 메시지 300개
  3) 지금 브랜치의 작업 하나 (2단계에서 열림)

[어느 프로젝트?]
  1) 전체 (추천)
  2) 직접 고르기 — 프로젝트별 메시지 수와 마지막 날짜를 보여 줌

[git 기록도 읽을까요?] (커밋과 테스트 파일을 읽어 「테스트에 기대값 확인이 있나」 같은 것을 봐요. 저장소 밖으로는 아무것도 보내지 않아요)
  1) 예 — 찾은 저장소: shop-api, admin-web, … (추천)
  2) 아니오 — 테스트·커밋에 관한 피드백이 빠져요

[짧은 문장 분류에 AI 를 쓸까요?] (내 메시지가 「고쳐 줘」인지 「왜?」인지, 같은 부탁을 되풀이했는지를 AI 가 한 줄씩 판정해요. 비밀값·이메일·전화번호를 가린 짧은 문장만 보내요)
  1) 쓴다 — 약 80k 토큰, 처음 한 번만 들고 다음부턴 새 메시지만 (추천)
  2) 안 쓴다 — 「같은 증상에 고쳐 줘 반복」, 「같은 부탁 반복」이 빠지고 비밀값·테스트 피드백만 나와요

[이번에 특히 보고 싶은 것이 있나요?] (고르면 그쪽 피드백을 먼저 보여 줘요)
  1) 알아서 — 시간이 가장 많이 샌 것부터 (추천)
  2) 막혔을 때 어떻게 하는지
  3) 끝났다는 걸 어떻게 확인하는지
  4) 일을 어떻게 맡기는지
  5) 규칙·자동 검사를 키우는지
```

AI 분류를 고르면 실제로 보내는 문장 예시 세 개를 가린 상태로 먼저 보여 주고 한 번 더 묻는다.
